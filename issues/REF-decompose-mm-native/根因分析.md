## 1. 结论先行

失败不是 `decompose_mm` pattern 错误命中，也不是该 pattern 的 replacement 计算错误。触发输入
`[2048, 2] @ [2, 2]` 是 M 阈值负例，transformed FX 正确保留 `aten.mm.default`，目标 counter 为 0。

首个真实分歧发生在之后的 lowering：PyTorch upstream 的 `_use_small_mm_pointwise` 是按 H200/cuBLAS
收益设计的启发式，却只排除了 CPU/MPS，没有排除 NPU。它把 AOTAutograd backward 中的 `mm_2`
展开为 `unsqueeze → mul → sum`，随后 `triton_experimental` 生成两个 pointwise kernel。该路径前向近似
正确、右梯度正确，但左梯度有 `4085/4096` 个元素不一致，最大绝对误差
`29.026336669921875`。

因此修复层必须是 NPU lowering guard，不能修改 `decompose_mm` 的 pattern、阈值或 replacement。

## 3. 为什么不是目标 pattern 的问题

PyTorch `decompose_mm` 在 post-grad FX pass 中注册。它只有在 `should_decompose_mm` 返回真时才计数并
替换图：

```python
# torch/_inductor/fx_passes/decompose_mem_bound_mm.py:267
@register_graph_pattern(
    CallFunction(aten.mm, Arg(), Arg()),
    pass_dict=construct_pattern_matcher_pass("decompose_mm_pass"),
)
def decompose_mm(match, mat1, mat2):
    def repl(mat1, mat2):
        return torch.sum(
            mat1[:, :, None] * mat2[None, :, :], dim=-2
        ).to(mat1.dtype)

    if should_decompose_mm(mat1, mat2):
        counters["inductor"]["decompose_mm"] += 1
        match.replace_by_example(repl, [mat1, mat2])
```

静态 accelerator 分支只接受 CUDA/XPU，同时要求 M 达到阈值：

```python
# torch/_inductor/fx_passes/decompose_mem_bound_mm.py:130
return (
    check_device(mat1, mat2, device="cuda")
    or check_device(mat1, mat2, device="xpu")
) and statically_known_true(
    mat1.shape[0] >= min_first_dimension_decomposition
) and statically_known_true(
    mat2.shape[0] < max_other_dimension_decomposition
) and statically_known_true(
    mat2.shape[1] < max_other_dimension_decomposition
)
```

本例的动态证据为 `decompose_mm=0`，transformed FX 仍是 `aten.mm.default`。GPU 参考中 M=2048 也属于
阈值负例，因而 GPU/NPU 在“目标 pattern 不改写”这一层行为一致。

## 4. 必要调用链

这是数值断言失败，不存在可引用的 Python exception traceback。下面是由注册源码、FX、生成代码和
失败断言共同确认的最短必要调用链；`[观测]` 表示有动态 artifact，`[源码]` 表示由固定 revision
的调用关系重建：

```text
npu_adapter.py::mm_fn(left, right)                         [源码]
  └─ torch.compile(..., npu_backend="triton_experimental") [观测]
      └─ Dynamo / AOTAutograd                              [源码]
          ├─ forward FX: aten.mm.default                   [观测]
          └─ backward FX: mm_2                             [观测]
              └─ post-grad decompose_mm handler            [源码+观测]
                  └─ should_decompose_mm(...) == False     [观测: counter=0]
                      └─ FX 保持 aten.mm.default            [观测]
                          └─ @register_lowering(aten.mm)
                             tuned_mm(...)                  [源码]
                              └─ mm_args(...)               [源码]
                                  └─ _use_small_mm_pointwise(
                                       M=2048,K=2,N=2,NPU)  [源码+观测]
                                      └─ True（修复前）     [由生成路径反证]
                                          └─ L.unsqueeze
                                             → L.mul
                                             → L.sum_       [源码]
                                              └─ NPU scheduler/codegen
                                                  └─ triton_unk_fused_mm_0/1
                                                               [观测]
                                                      └─ actual.sum().backward()
                                                          └─ assert_close(left_grad)
                                                              [观测: 失败]
```

后端修复的安装链是：

```text
TORCHINDUCTOR_NPU_BACKEND=triton_experimental
  └─ torch_npu._inductor._load_triton_experimental_backend()
      └─ triton_experimental._activate()
```

后端必须在导入/注册阶段选定并使用 fresh process；否则进程级 monkeypatch 生命周期会污染 OFF/ON

## 5. 首个分歧对应的 upstream lowering

`aten.mm` lowering 在 FX pattern 之后再次拥有一条独立的小矩阵分解路径：

```python
# torch/_inductor/kernel/mm.py:326,389
@register_lowering(aten.mm, type_promotion_kind=None)
def tuned_mm(mat1, mat2, out_dtype=None, *, layout=None):
    m, n, k, layout, mat1, mat2 = mm_args(
        mat1, mat2, layout=layout, out_dtype=out_dtype
    )

    if out_dtype is None and _use_small_mm_pointwise(m, k, n, layout):
        counters["inductor"]["decompose_mm_pointwise"] += 1
        mat1 = L.unsqueeze(mat1, -1)
        mat2 = L.unsqueeze(mat2, 0)
        return L.sum_(L.mul(mat1, mat2), axis=1)
```

启发式的注释明确写的是 H200/cuBLAS 收益，设备条件却只有 CPU/MPS 排除：

```python
# torch/_inductor/kernel/mm_common.py:197
def _use_small_mm_pointwise(m, k, n, layout) -> bool:
    """...
    cuBLAS launch overhead dominates ... faster (1.2-4.8x on H200).
    """
    if config.max_autotune or config.max_autotune_gemm:
        return False
    if layout.device.type in ("cpu", "mps"):
        return False
    skt = V.graph.sizevars.statically_known_true
    return skt(m >= 64) and skt(k < 5) and skt(n < 5)
```

NPU 满足 `M>=64,K<5,N<5`，所以误入一条未在 NPU 上建立正确性合同的 CUDA-oriented 路径。

## 7. 根因与非根因边界

根因：upstream small-MM heuristic 的设备适用范围宽于其验证范围，NPU experimental codegen 对其在
AOTAutograd backward 形成的 IR 没有保持正确性。

本轮能够证明首个分歧在 lowering，并能通过恢复 extern mm 消除错误；现有证据没有进一步把错误归因
到某一条 Triton 指令或编译器内部 pass。因此报告不虚构更深层的 compiler 根因。

明确排除：

- 不是 `decompose_mm` 错误命中：counter 为 0；
- 不是其 replacement 错误：replacement 没有执行；
- 不是 scheduler 拒绝：错误 kernel 已成功生成并运行；
- 不是设备运行异常：无启动异常，表现为稳定的梯度数值错误；
- 不是通过放宽容差可以接受的误差：最大绝对误差 29.0263，且 4085/4096 元素不一致。

## 8. 修复原则

最小修复应满足：

1. 只在 `layout.device.type == "npu"` 时返回 `False`；
2. CUDA/XPU 等设备仍委托 upstream 原函数；
3. 安装幂等，避免 repeated backend registration 叠加 wrapper；
4. 不改变 `decompose_mm` pattern 或 M/K/N 阈值；
5. 仅恢复可靠 extern mm，不声称启用了目标分解或获得性能收益。

具体补丁和验证见 [`修复验证报告.md`](修复验证报告.md)。
