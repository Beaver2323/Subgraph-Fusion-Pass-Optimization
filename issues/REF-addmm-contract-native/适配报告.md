## 1. 原生阻断

`TestPatternMatcher.test_addmm` 受 GPU-only suite 发现门阻断。它实际包含五个逻辑 case、两个 operand
顺序及正负 counter，不能把单一 matrix-bias 成功当成整个 addmm contract。

## 2. 最小适配

```python
# issues/REF-addmm-contract-native/npu_adapter.py:34-56
torch.npu.set_device("npu:0")
upstream.GPU_TYPE = "npu"
class Case(unittest.TestCase):
    test_addmm = upstream.TestPatternMatcher.test_addmm
```

adapter 直接运行完整上游 test body，并在 counter 断言处保存所有观察后再报告 mismatch；不改变
bias shape、operand 顺序、正负期望或安装态 `disable_addmm_fusion=True`。

## 3. 必要调用链

源码重建链：`Case.test_addmm → upstream five logical cases → torch.compile → post-grad addmm pattern
→ triton_experimental installed gate → correctness/counter assertions`。

## 4. 结果与边界

全部 eager/compiled 数值正确，但安装态正例 counter 为 0，故原测试总体按预期发生 counter mismatch；
正式 verdict 是 `EXPECTED_PRODUCT_DIVERGENCE`。P-018 live 候选另见[根因分析](根因分析.md)与
[修复验证报告](修复验证报告.md)，不能回写成安装态已启用。
