## 2. GPU/NPU为什么不同

```python
# 冻结 torch/_inductor/fx_passes/fuse_attention.py:358起，结构节选
# search: permute Q/K/V -> matmul -> div(inv_scale) -> add(attn_mask) -> softmax -> matmul
# replacement仍传递float型加法mask及原scale，不改输入以迎合后端kernel。
_scaled_dot_product_attention(q, k, v, attn_mask=attn_mask.to(dtype=query.dtype), scale=1.0/inv_scale)
```

GPU原件中的实际调用为：

```python

# run_2026_09_14_19_20_00_589365-pid_1671491/torchinductor/model__0_inference_0.0/output_code.py:191
# 节选，q/k/v/mask仅代指原件的reinterpret_tensor视图参数。

    q, k, v, mask, False, scale=0.3333333333333333,
```

NPU目标后的FX已经是 `bmm -> add(float mask) -> safe-softmax展开 -> bmm`。
生成代码实际调用两次`extern_kernels.bmm`及NPU Triton软最大值等kernel，不存在融合attention调用。
这属于**SDPA后端数学展开**，不是CPU回退，也不是未运行目标pattern。

```python
# evidence/t104-native-m26vaeeh/adapter/target-observations/*/fx_graph_transformed.py（节选）
bmm_default = torch.ops.aten.bmm.default(view_default, view_default_1)

# 中间为amax/sub/exp/sum/div，以及全-inf行的safe-softmax处理。

```

本机op-plugin源码 `ops/opapi/ScaledDotProductAttentionKernelNpuOpApi.cpp:288` 的融合候选条件只接受bool mask或无mask，
未满足时末尾走`at::_scaled_dot_product_attention_math`。这解释了float加法mask下的展开方向；
**该C++源码仅作机制对照，未将源码文件当成已绑定当前二进制构建的证明**，本轮运行判据来自真实FX/IR/output_code。
