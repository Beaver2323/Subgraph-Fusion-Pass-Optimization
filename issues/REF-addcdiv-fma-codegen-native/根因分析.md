# REF-addcdiv-fma-codegen-native 根因分析报告

> 更新时间：2026-09-08 07:51:59 CST（UTC+08:00）
> 当前阶段：低精度三臂完成；BF16 已纳入正式 FMA guard，FP16 已通过后端专属显式舍入
> lowering 修复。完整后续结论见 [FP16 精度修复报告](FP16精度修复报告.md)。
> NPU 后端：`triton_experimental`

## 测试目的

确认 post-grad 将 `div → mul → add` 重融合为 `aten.addcdiv`，并使 Inductor
生成 `tl.fma` 与 `triton.language.div_rn`。社区方法同时检查：

1. `addcdiv_fma_fused == 1`；
2. 生成代码包含 `tl.fma`；
3. 生成代码包含 `triton.language.div_rn`。

## 根因类型

`missing-dispatch`：`triton_experimental` 的编译器 pass/lowering 注册覆盖缺失。
这不是 eager `aten.addcdiv` NPU 算子内核缺失，也不是 CPU fallback 问题。

## 判定依据

### 1. NPU baseline 确实进入测试体但目标未生效

最小入口适配运行原社区方法后，首个产品断言失败：

```text
Expected 1 but got 0.
counters["inductor"]["addcdiv_fma_fused"] == 0
```

有效 baseline 日志：
`/home/z50063656/tmp/t078-npu-results/REF-addcdiv-fma-codegen-native/adapter-i6uo737w/`。

失败轮图模式证据显示：

- `fx_graph_readable.py` 与 `fx_graph_transformed.py` 均保留
  `aten.div.Tensor → aten.mul.Tensor → aten.add.Tensor`；
- `ir_pre_fusion.txt` / `ir_post_fusion.txt` 是普通逐点除、乘、加；
- `output_code.py` 生成普通 `/`、`*`、`+`，没有 `aten.addcdiv`、`tl.fma` 或
  `triton.language.div_rn`；
- 生成的是 NPU Triton kernel，没有 CPU/eager fallback。

### 2. 上游 device guard 只允许 CUDA/XPU

代码位置：`torch/_inductor/fx_passes/post_grad.py:2040-2093`。

```python
# torch/_inductor/fx_passes/post_grad.py:2048-2051
out_val = match.output_node().meta.get("val")
if not (
    isinstance(out_val, torch.Tensor)
    and out_val.device.type in ("cuda", "xpu")
):
    return False
```

因此同一合法浮点 pattern 在 NPU 上会被 generic upstream guard 排除。该 guard
不是产品对 NPU 的显式 disable；按项目规则应先做能力审核，再决定是否进行最小适配。

### 3. experimental fallback 会覆盖 upstream addcdiv lowering

`torch_npu/_inductor/triton_experimental/lowering_override_list.py` 没有把
`aten.addcdiv` 列入 `GENERATE_LIST`，统一 fallback 扫描会覆盖上游 lowering。
即使只放宽 FX device guard，重新插入的 `aten.addcdiv` 也不能稳定到达 FMA lowering。

同时，上游 `torch/_inductor/lowering.py:8551-8612` 自身也只在 CUDA/XPU 上选择
`ops.div_rn + ops.fma`，NPU 会走普通算术，因此不能直接复用其当前实现形成目标合同。

`/home/z50063656/tmp/t078-npu-results/REF-addcdiv-fma-codegen-native/candidate-oqd40mu8/`。

这证明 Triton Ascend 与当前 CANN/SOC 能编译并正确执行目标路径，缺口位于
`torch_npu` experimental 注册层，而非 Triton/CANN 能力不足。

以下是 2026-09-06 初验时的阶段判断：首次正式实现沿用了 upstream 的“任意浮点 dtype”范围。verify 的 FP16 近邻实际命中
FMA/div_rn，但 compiled 与 NPU eager 不再位级一致，最大绝对误差为 `0.03125`。
失败图显示 FP16 load 被提升为 FP32，在 FMA 完成后才于 store 舍入；该路径与 NPU
eager 的低精度舍入顺序不同。因此正式 NPU guard 已收紧为所有输入及输出均为 FP32，
当时将 FP16/BF16 一并保留原分解路径。2026-09-08 三臂证据进一步证明 BF16 合法，当前边界以文末

## 2026-09-08 低精度根因补充

> 更新时间：2026-09-08 07:51:59 CST（UTC+08:00）

后续 GPU dtype-only 参考和 NPU 六进程三臂归因推翻了“BF16 必须与 FP16 一并排除”的保守假设：
BF16 四路输出位级一致，可安全复用同一 exact lowering；FP16 的 OFF、分解、重融合 compiled 哈希
一致但均不同于 eager，说明误差发生在 addcdiv pass 之外的低精度 Triton/eager 语义边界。

因此 BF16 阶段先将 NPU guard 更新为 FP32/BF16，FP16 暂时阻断。后续已定位并修复 FP16
舍入边界；这个历史判断仍由 FX、前后 IR、
`output_code.py` 和输出哈希支撑，详见
[低精度三臂与 BF16 修复报告](低精度三臂与BF16修复报告.md)。原 FP32 missing-dispatch 根因仍然成立。

## 2026-09-09 FP16 `value=1` 独立回归诊断与修复

### 测试目的

`torch.addcdiv(..., value=1)` 在 decomposition 消去乘一后应保持
`aten.div.Tensor -> aten.add.Tensor`，不命中 addcdiv FMA 重融合；同时 FP16
compiled 结果必须与同设备 NPU eager 逐位一致。

### 根因类型

`behavior-mismatch`。这是 T-078 原 FP32 missing-dispatch 问题之后的一个独立低精度
边界问题：前者修复 `aten.addcdiv` 不可用的路由，本节修复普通
`aten.div.Tensor` 在融合 pointwise 代码中丢失 FP16 中间舍入的行为差异。

### 判定依据

修复前在 Ascend 910B2 上的同输入对比为：

| 指标 | 修复前 |
| --- | ---: |
| `addcdiv_fma_fused` | 0 |
| mismatch | 1176/4096 |
| 最大绝对误差 | 0.015625 |
| 生成代码中 FP16 quotient 舍入 | 0 次 |

FX 结构和 counter 都符合社区合同，首次分歧出现在 lowering 之后的 pointwise
代码生成：

```text
torch.addcdiv(value=1)
  -> CompositeImplicitAutograd decomposition
  -> aten.div.Tensor -> aten.add.Tensor
  -> post-grad PatternMatcherPass（不命中，counter=0）
  -> torch_npu triton_experimental aten.div.Tensor lowering
  -> Inductor Pointwise IR
  -> Triton Ascend output_code.py
```

修复前 `output_code.py` 中 quotient 保持 FP32 计算类型并直接参与加法：

```python
# evidence/FP16精度修复/20260909-current/value-one-failure/debug/output_code.py
tmp3 = tmp1 / tmp2
tmp4 = tmp0 + tmp3
tl.store(out_ptr0 + (x0), tmp4, x0mask)
```

NPU eager 的 `aten.div` 先产生一个 FP16 中间张量，再交给 `aten.add`；因此编译路径
必须在两个 op 边界之间恢复一次 FP16 round-trip。

### NPU 能力匹配评估

- 原图、修复图都能在 `triton_experimental` 生成并运行 kernel，不是 Triton/CANN
  能力缺失。
- 修复后 `output_code.py` 确实生成 `.to(tl.float16)`，且整个表达式仍在
  Triton kernel 内，没有 CPU fallback。
- 对应的明确 disable 只涉及其他 dtype/产品路径，不覆盖本 FP16 case；
  因此本问题可以且应当做最小源码修复。

### 关键代码变更

```python
# torch_npu/_inductor/triton_experimental/lowering.py
@register_lowering(
    aten.div.Tensor,
    broadcast=True,
    type_promotion_kind=ELEMENTWISE_TYPE_PROMOTION_KIND.INT_TO_FLOAT,
)
def npu_fp16_div(a, b):
    dtype = get_promoted_dtype(
        a,
        b,
        type_promotion_kind=ELEMENTWISE_TYPE_PROMOTION_KIND.INT_TO_FLOAT,
    )
    if dtype != torch.float16 or a.get_device().type != "npu":
        return original(a, b)

    def inner_fn(idx):
        quotient = ops.truediv(a_loader(idx), b_loader(idx))
        quotient = ops.to_dtype(
            quotient,
            torch.float16,
            src_dtype=torch.float32,
            use_compute_types=False,
        )
        return ops.to_dtype(
            quotient,
            torch.float16,
            src_dtype=torch.float16,
        )
```

修复后的 Triton 代码为：

```python
# evidence/FP16精度修复/20260909-fixed/value-one/output_code.py
tmp3 = (tmp1 / tmp2)
tmp4 = tmp3.to(tl.float16)
tmp5 = tmp4.to(tl.float32)
tmp6 = tmp0 + tmp5
tl.store(out_ptr0 + (x0), tmp6, x0mask)
```

### 修复理由

修复放在 torch_npu 的后端 lowering，而不是改 PyTorch 通用 decomposition 或恢复
`add(div) -> addcdiv` pattern：

- CUDA FP16 eager 允许 quotient 以 FP32 accumulator 语义继续计算，通用修改会改变 CUDA
  已有的位级合同。
- NPU eager 在 `div` op 边界物化 FP16 结果，差异是 NPU Triton 后端的语义补齐。
- 恢复 addcdiv 重融合会错误地使 `addcdiv_fma_fused=1`，违反社区对 value=1
  已经定义的不命中结构合同。

### 代码差异

最小产品差异是新增一个 dtype/device 路由：

```diff
+if dtype != torch.float16 or a.get_device().type != "npu":
+    return original(a, b)
+quotient = ops.truediv(a_loader(idx), b_loader(idx))
+quotient = ops.to_dtype(
+    quotient, torch.float16,
+    src_dtype=torch.float32,
+    use_compute_types=False,
+)
+return ops.to_dtype(
+    quotient, torch.float16,
+    src_dtype=torch.float16,
+)
```

FP32、BF16和非 NPU 路径仍委托原 upstream lowering；未改 pattern guard、未引入
skip、未增加 eager/CPU fallback。
