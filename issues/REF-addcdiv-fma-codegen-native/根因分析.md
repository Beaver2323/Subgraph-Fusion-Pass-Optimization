# REF-addcdiv-fma-codegen-native 根因分析报告

> 更新时间：2026-09-08 07:51:59 CST（UTC+08:00）
> 当前阶段：低精度三臂完成；BF16 已纳入正式 guard，FP16 因既有 compiled/eager 精度差异继续阻断。
> NPU 后端：`triton_experimental`

## 测试目的

确认 post-grad 将 `div → mul → add` 重融合为 `aten.addcdiv`，并使 Inductor
生成 `tl.fma` 与 `triton.language.div_rn`。社区方法同时检查：

1. `addcdiv_fma_fused == 1`；
2. 生成代码包含 `tl.fma`；
3. 生成代码包含 `triton.language.div_rn`。

## 根因类型

`missing-dispatch`：`triton_experimental` 的编译器 pass/lowering 注册覆盖缺失。
这不是 eager `aten.addcdiv` NPU 算子内核缺失，也不是 CPU fallback 问题。

## 判定依据

### 1. NPU baseline 确实进入测试体但目标未生效

最小入口适配运行原社区方法后，首个产品断言失败：

```text
Expected 1 but got 0.
counters["inductor"]["addcdiv_fma_fused"] == 0
```

有效 baseline 日志：
`/home/z50063656/tmp/t078-npu-results/REF-addcdiv-fma-codegen-native/adapter-i6uo737w/`。

失败轮图模式证据显示：

- `fx_graph_readable.py` 与 `fx_graph_transformed.py` 均保留
  `aten.div.Tensor → aten.mul.Tensor → aten.add.Tensor`；
- `ir_pre_fusion.txt` / `ir_post_fusion.txt` 是普通逐点除、乘、加；
- `output_code.py` 生成普通 `/`、`*`、`+`，没有 `aten.addcdiv`、`tl.fma` 或
  `triton.language.div_rn`；
- 生成的是 NPU Triton kernel，没有 CPU/eager fallback。

### 2. 上游 device guard 只允许 CUDA/XPU

代码位置：`torch/_inductor/fx_passes/post_grad.py:2040-2093`。

```python
# torch/_inductor/fx_passes/post_grad.py:2048-2051
out_val = match.output_node().meta.get("val")
if not (
    isinstance(out_val, torch.Tensor)
    and out_val.device.type in ("cuda", "xpu")
):
    return False
```

因此同一合法浮点 pattern 在 NPU 上会被 generic upstream guard 排除。该 guard
不是产品对 NPU 的显式 disable；按项目规则应先做能力审核，再决定是否进行最小适配。

### 3. experimental fallback 会覆盖 upstream addcdiv lowering

`torch_npu/_inductor/triton_experimental/lowering_override_list.py` 没有把
`aten.addcdiv` 列入 `GENERATE_LIST`，统一 fallback 扫描会覆盖上游 lowering。
即使只放宽 FX device guard，重新插入的 `aten.addcdiv` 也不能稳定到达 FMA lowering。

同时，上游 `torch/_inductor/lowering.py:8551-8612` 自身也只在 CUDA/XPU 上选择
`ops.div_rn + ops.fma`，NPU 会走普通算术，因此不能直接复用其当前实现形成目标合同。

## NPU 能力匹配评估

能力探针采用与社区用例相同的 FP32/scalar 合同，并在 fallback 之后窄注册
`aten.addcdiv.default` lowering。结果：

| 检查项 | 结果 |
|---|---|
| 社区命中计数 | `1` |
| 生成代码包含 `tl.fma` | 是 |
| 生成代码包含 `triton.language.div_rn` | 是 |
| 派生 `value=2.0` compiled vs eager | bitwise equal |
| 最大绝对误差 | `0.0` |
| CPU fallback / skip | 均无 |

候选日志：
`/home/z50063656/tmp/t078-npu-results/REF-addcdiv-fma-codegen-native/candidate-oqd40mu8/`。

这证明 Triton Ascend 与当前 CANN/SOC 能编译并正确执行目标路径，缺口位于
`torch_npu` experimental 注册层，而非 Triton/CANN 能力不足。

以下是 2026-09-06 初验时的阶段判断：首次正式实现沿用了 upstream 的“任意浮点 dtype”范围。verify 的 FP16 近邻实际命中
FMA/div_rn，但 compiled 与 NPU eager 不再位级一致，最大绝对误差为 `0.03125`。
失败图显示 FP16 load 被提升为 FP32，在 FMA 完成后才于 store 舍入；该路径与 NPU
eager 的低精度舍入顺序不同。因此正式 NPU guard 已收紧为所有输入及输出均为 FP32，
当时将 FP16/BF16 一并保留原分解路径。2026-09-08 三臂证据进一步证明 BF16 合法，当前边界以文末
“低精度根因补充”为准。

        return ops.add(self_val, quotient)

## 2026-09-08 低精度根因补充

> 更新时间：2026-09-08 07:51:59 CST（UTC+08:00）

后续 GPU dtype-only 参考和 NPU 六进程三臂归因推翻了“BF16 必须与 FP16 一并排除”的保守假设：
BF16 四路输出位级一致，可安全复用同一 exact lowering；FP16 的 OFF、分解、重融合 compiled 哈希
一致但均不同于 eager，说明误差发生在 addcdiv pass 之外的低精度 Triton/eager 语义边界。

因此当前修复将 NPU guard 更新为 FP32/BF16，FP16 继续阻断。这个判断同时由 FX、前后 IR、
`output_code.py` 和输出哈希支撑，详见
[低精度三臂与 BF16 修复报告](低精度三臂与BF16修复报告.md)。原 FP32 missing-dispatch 根因仍然成立。
