## 1. 为什么需要补测

社区 `test_addcdiv_fma_uses_fma_and_div_rn` 只以默认 FP32 运行，但上游
`_fuse_addcdiv_to_fma` 的 dtype 范围是浮点类型。T-078 早期把 NPU 能力收窄为 FP32 后，不能仅凭
一轮 FP16 误差就同时排除 FP16 和 BF16。因此本轮先在 GPU 上仅改变 dtype，随后在 NPU 上用相同
输入做 OFF、显式分解、重融合三臂归因。

GPU 派生 case 没有改变社区 shape、标量或验收语义：

```python
# runners/t078_addcdiv_dtype_reference.py:44-82

self.assertTrue(torch.equal(actual, expected))
self.assertEqual(counters["inductor"].get("addcdiv_fma_fused", 0), 1)
self.assertIn("tl.fma", code)
self.assertIn("triton.language.div_rn", code)
```

GPU partial reference `reference-20260907T230819+0800-iuahayld` 为 2/2 passed，FP16、BF16
均完成 `div → mul → add` 到 `aten.addcdiv` 的改写，并通过位级、counter、FMA 和 `div_rn` 断言。

## 2. NPU 三臂方法与调用栈

六个 fresh process 均在导入 `torch` 前选择 `triton_experimental`，并从 CPU 固定随机数发生器
生成输入，以保证跨进程输入哈希相同：

```python

    raise RuntimeError("必须在导入 torch 前指定 triton_experimental")

generator = torch.Generator(device="cpu")
generator.manual_seed(20260908)
...
return tuple(tensor.to("npu") for tensor in tensors), hashes
```

三个 arm 的含义：

- `OFF`：输入仍是 `torch.addcdiv`，但产品 FP16 guard 或候选关闭使目标重融合不发生；
- `decomposed`：直接编译 `s + (t1 / t2) * 2.0`；
- `re-fused`：只在当前 fresh process 安装候选 pattern/lowering，强制观察 FMA 路径。

必要调用栈如下：

```text
run_lowp_three_arm.py
  -> fresh subprocess × (2 dtype × 3 arm)
  -> verify_lowp_three_arm.py
  -> register_inductor_npu()
  -> torch.compile(..., fullgraph=True)
  -> post_grad_passes
  -> fx_passes._install_addcdiv_fma_pass
  -> is_npu_addcdiv_fma_eligible
  -> npu_fuse_addcdiv_to_fma
  -> lowering._register_npu_addcdiv_lowering
  -> ops.div_rn + ops.fma
  -> Triton Ascend output_code.py
```

`arm_result.json` 同时记录输入、eager、compiled 哈希、位级相等、误差、目标 counter 和生成代码
token；FX、前后 IR 与 `output_code.py` 均随结果归档。

## 3. 三臂结果

| dtype | OFF vs eager | 分解 vs eager | 重融合 vs eager | 三条 compiled 相互关系 | 结论 |
| --- | --- | --- | --- | --- | --- |
| FP16 | 非位级；max `0.0625`；1187/4096 不同 | 同左 | 同左；counter=1，FMA/div_rn | 三者 SHA256 完全相同 | 融合没有增加误差；既有 Triton 编译路径与 NPU eager 存在精度语义差异 |
| BF16 | 位级一致；误差 0 | 位级一致；误差 0 | 位级一致；counter=1，FMA/div_rn | 三者及 eager SHA256 完全相同 | 可安全启用重融合 |

FP16 三条 compiled 输出 SHA256 均为
`0fb03299d47799b0d9b1bb54b1313e2c2b7efae8823f8a76b575fd99b6c505c7`，eager 为
`189ea25003f9aaa9b842765ef513d5a7c092e0e2753cb613d11f2a4f08e96609`。因此不能把误差归因给
addcdiv 重融合，也不能通过关闭这个 pattern 修复底层精度问题。

编译证据也能解释三条结果为什么一致。OFF 路径把 FP16 load 提升为 FP32，执行普通除乘加后只在
store 时写回 FP16：

```python
# evidence/低精度三臂/float16/off/output_code.py:99-106
tmp0 = tl.load(in_ptr0 + (x0), x0mask).to(tl.float32)
tmp1 = tl.load(in_ptr1 + (x0), x0mask).to(tl.float32)
tmp2 = tl.load(in_ptr2 + (x0), x0mask).to(tl.float32)
tmp3 = (tmp1 / tmp2)
tmp4 = tl.full([1], 2.0, tl.float32)
tmp5 = tmp3 * tmp4
tmp6 = tmp0 + tmp5
tl.store(out_ptr0 + (x0), tmp6, x0mask)
```

重融合路径只将算术表达改成精确除法与 FMA，仍是 FP32 中间量、末端写回：

```python
# evidence/低精度三臂/float16/re-fused/output_code.py:95-101
tmp0 = tl.load(in_ptr0 + (x0), x0mask).to(tl.float32)
tmp1 = tl.load(in_ptr1 + (x0), x0mask).to(tl.float32)
tmp2 = tl.load(in_ptr2 + (x0), x0mask).to(tl.float32)
tmp3 = triton.language.div_rn(tmp1, tmp2)
tmp4 = tl.full([1], 2.0, tl.float32)
tmp5 = tl.fma(tmp4, tmp3, tmp0)
tl.store(out_ptr0 + (x0), tmp5, x0mask)
```

这是一项真实的 FP16 编译/eager 精度缺口，但不是本 addcdiv pass 新引入的缺陷。修复需要继续
追踪 Triton 低精度逐点语义与 eager 算子舍入边界，不能在本 pattern 中加容差或伪造通过。

## 4. BF16 最小修复

动态三臂证明 BF16 可用后，只扩大 NPU-only pattern 的 dtype guard，lowering 和其他设备均不改：

```python
# torch_npu/_inductor/triton_experimental/fx_passes.py:795-818
def is_npu_addcdiv_fma_eligible(match: Match) -> bool:
    inp_val = match.kwargs["inp"].meta.get("val")
    supported_dtypes = (torch.float32, torch.bfloat16)
    ...
    and out_val.device.type == "npu"
    and out_val.dtype in supported_dtypes
```

安装位置仍在 `overrides.apply_npu_overrides()`，lowering 仍是 exact overload：

```python
# torch_npu/_inductor/triton_experimental/lowering.py:134-157
@register_lowering(aten.addcdiv.default, broadcast=True)
def npu_addcdiv(self, tensor1, tensor2, *, value=1):
    ...
    quotient = ops.div_rn(t1_val, t2_val)
    ...
    return ops.fma(value_expr, quotient, self_val)
```

正式源码 overlay 近邻验证：BF16 `bitwise_equal=true`、最大误差 0、期望/实际 counter 均为 1；
FP16 期望/实际 counter 均为 0，证明 guard 没有被误放宽。没有新增 CPU fallback、skip 或 disabled
test。

## 5. BF16 性能处置

社区没有对应的 addcdiv pass benchmark，因此复用社区功能 case 的 `64×64`、`value=2`，只把 dtype
改为 BF16，并添加目标级 OFF/ON、三轮 fresh process、host/NPU Event 和显存测量。它测量单个
compiled 子图的端到端调用，不代表完整模型收益。

```python
# runners/t078_performance_worker.py:179-218
def make_workloads(unit, addcdiv_dtype="float32"):
    dtype = {
        "float32": torch.float32,
        "bfloat16": torch.bfloat16,
    }[addcdiv_dtype]
    ...
    return torch.addcdiv(inp, tensor1, tensor2, value=value)
```

三轮中 OFF target hit 均为 0，ON 均为 1；两臂均与 eager 位级一致。结果：

| 指标 | ON 相对 OFF |
| --- | ---: |
| host p50 | 改善 `0.16%` |
| host p99 | 改善 `3.59%` |
| NPU Event p50 | 回退 `0.78%` |
| NPU Event p99 | 改善 `9.86%` |
| allocated / reserved | `0 / 0` bytes |
| wrapper dispatch | 无变化 |

按项目阈值既未达到稳定改善，也未达到 5% 回退门槛，判定 `PERF_NEUTRAL`，保持 BF16 能力启用。
FP16 因功能精度未闭环，明确免测性能。
