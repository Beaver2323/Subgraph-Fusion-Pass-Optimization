## 1. Pattern 是什么，为什么要做

`torch.addcdiv(input, tensor1, tensor2, value=v)` 是 CompositeImplicitAutograd 算子。进入
Inductor 后通常先被分解为：

```text
tensor1 / tensor2 -> quotient
quotient * value  -> scaled
input + scaled    -> output
```

PyTorch 的 post-grad pattern 再识别这条链，并重建一个 `aten.addcdiv` 节点，使专用 lowering
能够选择更精确或更高效的实现：

```python
# PyTorch: torch/_inductor/fx_passes/post_grad.py:2064-2093
@register_graph_pattern(
    CallFunction(
        aten.add.Tensor,
        KeywordArg("inp"),
        CallFunction(
            aten.mul.Tensor,
            CallFunction(aten.div.Tensor, KeywordArg("t1"), KeywordArg("t2")),
            KeywordArg("value"),
        ),
    ),
    pass_dict=pass_patterns[2],
    extra_check=_is_addcdiv_fma_eligible,
)
def _fuse_addcdiv_to_fma(match, inp, t1, t2, value):
    def repl(inp, t1, t2, value):
        return torch.ops.aten.addcdiv(inp, t1, t2, value=value)

    counters["inductor"]["addcdiv_fma_fused"] += 1
    match.replace_by_example(repl, [inp, t1, t2, value])
```

上游将该 pattern 限定为 CUDA/XPU，并按 `div_rn + FMA` 设计。NPU 不能只把 device guard
机械扩为 `npu`：同一个数学表达式在 FP16 上有不同的可观察舍入边界。

## 2. GPU 与 NPU 原始行为

GPU A100 的 dtype-only 派生社区 case 中，FP16 能命中上游 pattern，生成 `div_rn + tl.fma`，并与
CUDA eager 逐位一致。GPU 证据来自
`results/incoming/T-078/BF16-FP16-text-handoff.json`。

NPU eager 走 op-plugin 的 `aclnnAddcdiv`：

```cpp
// torch_npu third_party/op-plugin/op_plugin/ops/opapi/
// AddcdivKernelNpuOpApi.cpp:74-88
at::TensorList tensors = {self, tensor1, tensor2};
auto high_type = at::native::result_type(tensors);
...
at::Tensor result = npu_preparation::apply_tensor_without_format(
    output_size, self.options().dtype(high_type));
EXEC_NPU_CMD(aclnnAddcdiv, self, tensor1, tensor2, value, result);
```

修复前，用完全相同输入执行 OFF、显式分解、候选重融合三个 fresh process，三条 compiled 路径
彼此相同，但都与 eager 不一致：最大绝对误差 `0.0625`，`4096` 个元素中有 `1187` 个不同。
这证明错误不由重融合新增，而是原 Triton 分解路径把 FP16 中间计算提升到 FP32 后只在最终 store
舍入，丢失了 NPU eager 的低精度边界。

```python
# 修复前 evidence/低精度三臂/float16/off/output_code.py:99-106
tmp0 = tl.load(in_ptr0 + (x0), x0mask).to(tl.float32)
tmp1 = tl.load(in_ptr1 + (x0), x0mask).to(tl.float32)
tmp2 = tl.load(in_ptr2 + (x0), x0mask).to(tl.float32)
tmp3 = (tmp1 / tmp2)
tmp4 = tl.full([1], 2.0, tl.float32)
tmp5 = tmp3 * tmp4
tmp6 = tmp0 + tmp5
tl.store(out_ptr0 + (x0), tmp6, x0mask)
```

专项语义探针进一步证明 NPU eager 等价于：

```text
q = fp16(tensor1 / tensor2)
p = fp16(q * fp16(value))
out = fp16(input + p)
```

其中 Python 标量也要先量化到 FP16；`0.3`、`1.3`、`7.7` 等不可精确表示的字面量能暴露这一点。

## 3. 根因与首次分歧

必要调用栈：

```text
torch.addcdiv
  -> CompositeImplicitAutograd decomposition: div -> mul -> add
  -> post_grad PatternMatcherPass[2]
  -> NPU npu_fuse_addcdiv_to_fma / npu_fuse_addcdiv_value_one
  -> aten.addcdiv.default
  -> _register_npu_addcdiv_lowering
  -> Inductor Pointwise IR
  -> Triton Ascend codegen
  -> output_code.py
```

首次分歧位于 lowering/codegen，而不是 FX pattern：修复前 FX 重融合是正确的，但 FP16 lowering
错误沿用了 FP32/BF16 的 `div_rn + FMA` 合同。FMA 只在最后一次舍入，无法复现 NPU eager 在除法和
乘法后的两次低精度舍入。

另一个真实缺口是 `value=1`。分解器会消去乘一，FX 只剩 `input + tensor1/tensor2`，因此原
`add(mul(div, value))` pattern 无法命中。它需要一个语义等价但结构不同的 NPU 专属 pattern。

## 4. 最小源码修复

### 4.1 FP16 专属精确 lowering

FP32/BF16 继续使用已经验证的 `div_rn + FMA`；只有 FP16 在一个 Triton kernel 内显式恢复两次
舍入。具体 Python 标量在编译期量化，避免不可精确字面量再次被 FP32 解释：

```python
# torch_npu/_inductor/triton_experimental/lowering.py:156-200
if dtype == torch.float16:
    quotient = t1_val / t2_val
    quotient = ops.to_dtype(
        quotient, torch.float16,
        src_dtype=torch.float32,
        use_compute_types=False,
    )
    quotient = ops.to_dtype(
        quotient, torch.float16, src_dtype=torch.float16,
    )
    quantized_value = torch.tensor(value, dtype=torch.float16).item()
    value_expr = ops.constant(quantized_value, dtype)
    product = ops.mul(quotient, value_expr)
    product = ops.to_dtype(
        product, torch.float16,
        src_dtype=torch.float32,
        use_compute_types=False,
    )
    product = ops.to_dtype(
        product, torch.float16, src_dtype=torch.float16,
    )
    return ops.add(self_val, product)

quotient = ops.div_rn(t1_val, t2_val)
...
return ops.fma(value_expr, quotient, self_val)
```

FP16 pattern 只接受经过本轮证明的具体 Python `int/float` 标量；tensor-valued 或未证明的符号
标量不会进入该重融合。

### 4.2 `value=1` 的消乘结构

```python
# torch_npu/_inductor/triton_experimental/fx_passes.py:847-871
@register_graph_pattern(
    CallFunction(
        aten.add.Tensor,
        KeywordArg("inp"),
        CallFunction(
            aten.div.Tensor,
            KeywordArg("t1"),
            KeywordArg("t2"),
        ),
    ),
    pass_dict=post_grad.pass_patterns[2],
    extra_check=is_npu_addcdiv_fma_eligible,
)
def npu_fuse_addcdiv_value_one(match, inp, t1, t2):
    def repl(inp, t1, t2):
        return aten.addcdiv(inp, t1, t2, value=1)

    counters["inductor"]["addcdiv_fma_fused"] += 1
    match.replace_by_example(repl, [inp, t1, t2])
```

该补充分支仍受 NPU device、浮点 dtype 和 scalar guard 约束，不改变 CUDA/XPU pattern，也没有
增加 CPU fallback、skip 或 disabled test。

## 5. 修复后的 FX、IR 与代码证据

`value=2` 的 transformed FX 已重新出现 `aten.addcdiv.default`：

最终生成代码保留了 NPU eager 的低精度边界：

```python
# evidence/FP16精度修复/value-two/output_code.py:95-106
tmp0 = tl.load(in_ptr0 + (x0), x0mask).to(tl.float32)
tmp1 = tl.load(in_ptr1 + (x0), x0mask).to(tl.float32)
tmp2 = tl.load(in_ptr2 + (x0), x0mask).to(tl.float32)
tmp3 = (tmp1 / tmp2)
tmp4 = tmp3.to(tl.float16)
tmp5 = tmp4.to(tl.float32)
tmp6 = tl.full([1], 2.0, tl.float32)
tmp7 = tmp5 * tmp6
tmp8 = tmp7.to(tl.float16)
tmp9 = tmp8.to(tl.float32)
tmp10 = tmp0 + tmp9
tl.store(out_ptr0 + (x0), tmp10, x0mask)
```

这意味着“pass 生效”由三类证据共同确认：FX 已重融合、counter 为 1、最终代码包含要求的两次
FP16 round。不能因为 FP16 最终代码不含 `tl.fma` 就判为未生效；不使用 FMA 正是该后端精度修复
的设计要求。

## 7. 性能边界

本轮不把 FP16 写成 `PERF_IMPROVED`、`PERF_NEUTRAL` 或 `PERF_REGRESSED`。原因不是“FP16 未修”，
而是修复前目标 OFF 路径已经不满足与 NPU eager 等价，不能作为合法收益分母。拿错误的 OFF 与正确的
ON 比速度会制造不可解释的 pass 收益。

因此正式处置为：`CORRECTNESS_REPAIR_COMPLETE_NO_VALID_PRE_FIX_OFF_DENOMINATOR`。后续可以记录
修复后 ON 与 NPU eager 的信息性耗时，但不得把它当成该 pattern 的 OFF/ON 收益。若未来获得同语义、
仅关闭重融合的合法 FP16 OFF 实现，再补正式三轮性能对比。
