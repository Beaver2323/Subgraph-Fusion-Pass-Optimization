# T-096：为什么 log2+ceil 改成位运算

> 更新时间：2026-09-11 18:44 CST（UTC+08:00）。Pass已修复，原合同完成；额外范围部分对齐，局部性能回退。

这是 MX scaling 的 FP32→E8M0 uint8 编码合同：对正正规数向上取二进制指数，夹到有限范围后加偏置127。

```python
# 冻结 torch/_inductor/fx_passes/misc_patterns.py:173-213
# 原图：(clamp(ceil(log2(inp)), -127, 127) + 127).to(uint8)
bits = inp.view(torch.int32)  # 读IEEE754位，不是数值转换
encoded = torch.clamp(((bits >> 23) & 255) + ((bits & 0x7FFFFF) != 0).int(), 0, 254).to(torch.uint8)
```

| 路径 | 普通7项输入 | 2的幂上方1 ULP | 是否已部署 |
| --- | --- | --- | --- |
| GPU A100 社区原生 | 数值通过、位运算改写 | 8项/7项数学oracle通过 | reference，不是NPU产品 |
| NPU 修复前 | 数值通过，但无目标改写 | 分别5项/4项编码低1；compiled=eager仍然是错的 | 旧安装态证据保留 |
| NPU 隔离候选 | 改写+数值通过 | 原数学oracle3/3 case全部通过 | 历史候选，不代替安装态 |
| NPU Pass已安装修复 | 改写+数值通过 | 原3例全部通过，边界有意不同于错误eager | NEWLY_SUPPORTED，未社区合入 |

功能完全复用社区三个原方法，保留输入和uint8精确相等断言，只作设备入口适配。NPU实际代码是 view(dtype) / 右移图内extern加位掩码/夹紧Triton核，不与CUDA kernel逐行相同。
正规FP32的指数是精确位域：尾数为0即2的整数幂，不进位；非0即介于两个幂之间，进位。这发生在post-grad、lowering和autotune之前，不是调参修复。

```python
# 产品 torch_npu/_inductor/triton_experimental/e8m0.py:25，NPU补充保护
subnormal = (mantissa > 0x400000).to(torch.int32)
encoded = torch.where(exponent == 0, subnormal, normal)
invalid = (bits < 0) | ((exponent == 255) & (mantissa != 0))
return torch.where(invalid, 0, encoded).to(torch.uint8)
```

原候选无法从dtype/device元数据证明输入全为正正规数，直接全域注册不安全。产品修复另处理subnormal的2^-127阈值，负值/NaN保留已测NPU旧行为0，+inf饱和254。
22项域检查和1016项正规指数/尾数组合通过；这些是NPU派生扩展，尚无CUDA邻接实测，故`PARTIAL_ALIGNED`，不增加冻结分母。CPU/FP16/BF16仍不命中，不代表低精度全域支持。

## 性能来源与结果

性能复用社区普通7值 `[1,2,4,3,1.5,.5,.25]`，精确开关独立新进程OFF/ON，两侧数学正确才计时。10次预热、100样本、OFF1/ON1/ON2/OFF2/OFF3/ON3；编译和显存单列。
测的是派生目标子图微基准，不是社区原生benchmark，也不是模型端到端。错误边界OFF未用于算收益。
