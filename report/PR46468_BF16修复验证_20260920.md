# PR 46468：addcdiv 精度问题修复结果

**这次发现的 BF16 精度问题已修复。修复后的 17 项专项测试全部通过，没有失败或跳过。** 测试完成时间：2026-09-20 23:33（北京时间）。代码和测试已推送到 PR 46468；2026-09-21 合并主线后再次执行 17 项，全部通过。见[合并后复测](pr-validation-20260920/master-merge-46468/README.md)及[流水状态](四个PR推送与流水状态_20260921.md)。

问题出在下面这个计算，其中 a、b、c 都是 BF16 张量：

```python
torch.addcdiv(a, b, c, value=0.1)
# 计算含义：a + 0.1 * (b / c)
```

直接在 NPU 上运行，与用 `torch.compile` 编译后运行，结果不一致。原测试共比较 4096 个输出值，其中 374 个不同，最大的差值是 0.015625。

原因是两条执行路径对系数 `0.1` 的处理不同。BF16 无法精确保存 0.1，转换后实际得到的是 **0.10009765625**。直接运行时使用这个转换后的值；原来的编译代码却按 FP32 保存 0.1，得到一个更接近 0.1 的值。虽然都写作 `value=0.1`，实际参与计算的系数不同，最终输出也就不同。

本次在编译代码中补上了这一步转换：**BF16 输入使用的系数，先转成 BF16，再参与后续计算。** 修改位置是 `torch_npu/_inductor/triton_experimental/lowering.py`。生成代码中已确认使用 0.10009765625；原来失败的同一个测试现在通过，374 个输出差异全部消除。

为了确认其他输入也能正常工作，又执行了以下测试。所有测试都要求编译后与直接运行的输出逐元素相等，允许误差为 0。

| 测试内容 | 数量 | 结果 |
| --- | ---: | --- |
| BF16，系数分别为 0.1、0.3、1.3、2.0、-0.75 | 5 | 全部通过 |
| FP16，同样的五种系数 | 5 | 全部通过 |
| FP32，同样的五种系数 | 5 | 全部通过 |
| FP16，系数为 1 | 1 | 通过 |
| FP16，输入包含间隔切片和不同形状的张量 | 1 | 通过 |
| **合计** | **17** | **全部通过，无跳过** |

这次补测 0.3 和 1.3，是因为它们与 0.1 一样，转换成 BF16 后会发生舍入。此前通过的 2.0 和 -0.75 可以被 BF16 精确表示，因此没有暴露这个问题。

这些结果证明本次修改解决了上述测试中的精度差异。此次修复后执行的是 addcdiv 专项测试，尚未重新执行完整模型流水，也未评估本次修改的性能变化。

测试使用 CANN 9.2、NPU 0/1 和 `triton_experimental` 后端。每个用例单独启动进程并关闭编译缓存，确保实际执行新生成的代码。测试代码基于 PR 提交 `cc0ded239cb1bad9981cf62f48adea79a5c79402`，加上本次修复；编译器相关 Python 文件使用独立副本，NPU 二进制库沿用现有安装版本，没有重新构建整个安装包。
