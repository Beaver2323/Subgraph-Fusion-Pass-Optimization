## 一次有效的 harness 失败

首轮 worker 在默认 grad-enabled 上下文运行，compiled 数值正确但目标 pass 调用数为 0。
失败用例的 `output_code.py` 仍包含 sum 对应 Triton kernel。源码核对确认 POST driver 用
`not torch.is_grad_enabled()` 判断 inference，所以跳过是预期行为。worker 随后只把
reference、compile 和执行包入 `torch.no_grad()`，没有修改产品 mode 逻辑。

这个分支提醒后续审计：没有 requires-grad 输入不等于 custom pass 所定义的推理模式；
必须显式记录 grad mode。

### 为什么数值正确仍然失败

eager `sum` 和 `cat` 都返回与输入不同的新 storage；触发两个 pass 后，compiled wrapper
却直接返回输入。两项的 dtype、shape、stride 和数值完全相同，但用户在图外修改输出时会
连带修改输入，违反 eager alias 语义。对应失败 `output_code.py` 均明确返回输入参数。

因此 `fold_reduce` 和 `cat_to_view_pass` 停止性能测试，进入已登记的 T-029 correctness
修复；不得把删除节点或误差为 0 写成“可用”。其他三个 not-reached positive 只说明当前
default pipeline 已在更早阶段完成等价规范化，不能把收益归因给目标 pass。

## T-029 至 T-031 最终闭环

T-029 先为两个错误 identity replacement 插入 contiguous clone，并补充 dtype/stride/
storage alias 门禁。新 wheel 安装后 33/33 个 FX 测试及四个 NPU 正负例通过，说明 clone
方案在功能上可用。T-030 随后使用三轮 fresh-process pass-on/pass-off paired benchmark：

| pass | p50 | p99 | task | additional allocated peak | 结论 |
|---|---:|---:|---:|---:|---|
| `fold_reduce -> clone` | -3.06% | -6.72% | 1→1 | 0 B | 正确但性能回退 |
| `cat_to_view -> clone` | +2.29% | -0.78% | 3→1 | -4,195,840 B | 延迟中性、资源有益 |

T-031 因而让 `fold_reduce` 保留原 sum，不再执行这条折叠；最终 wheel 中 positive/negative
均为 sum `1→1`、clone `0`，数值、dtype、stride、alias 全部通过。`cat_to_view_pass`
保留 clone 修复，positive 为 cat `1→0`、clone `0→1`，negative 为 cat `1→1`，同样
全部通过。最终 verdict：

- `fold_reduce`：`supported-pass-disabled-performance-rejected`；现有 sum 更快，不写
  手工 Triton copy。
- `cat_to_view_pass`：`supported-neutral-resource-beneficial`；保留 correctness 修复和
  task/显存收益，但不冒充超过 10% 的 latency beneficial。
- `fold_expand`、`repeat_to_expand_pass`：功能正负例通过，性能仍待测。
- `view_fold_pass`、`fold_slice`、`fold_four_op_pass`：当前正例未到达目标 pass，保持
  reachability-neutral，不归因性能。
