## 2. 静态合同与根因

基线静态合同确认主图使用 `NPUWrapperCodeGen`，子图 factory 保留上游
`SubgraphPythonWrapperCodegen`；NPU header 绑定快速 allocator，allocation 前仍执行 memory
lifecycle tracking。P-019/P-024 安装包与当前基线 wrapper SHA256 一致。

问题位于 `memory_plan_reuse()`：旧实现为容忍 rsplit 产生的 `WorkspaceArg`，把上游实现完整
复制到 NPU override，只将末尾输出检查改为安全 `getattr`。PyTorch 2.14 上游随后增加：

- `peak_estimate_stack`；
- `V.set_graph_handler(...)`；
- 每个 subgraph 独立 `EfficientPeakEstimate`。

NPU copy 没有这些逻辑。继续逐行同步会让同类漂移反复发生；直接删除 override 又会让
`WorkspaceArg` 在上游的 `node.name` 读取处抛 `AttributeError`。

P-025 的边界是：只要最后一行是 `MemoryPlanningLine` 且其 node 没有 `.name`，就先弹出；
named buffer 留给上游按 graph output 规则处理。workspace 不是 graph output，因而该预处理与
旧实现意图一致，其余当前及后续 planner 行为由上游实现负责。静态合同最终 18/18 通过。

## 5. 真实 NPU 生成图

### Pointwise wrapper

安装态 fresh-process pointwise 进入 `triton_experimental`，生成 1 个 Triton kernel，输出
allclose，max absolute diff `1.192093e-07`。生成 wrapper 含 3 次
`empty_strided_npu` 文本命中，实际加载 wrapper 与 P-025 哈希一致。

### Outer-rsplit workspace

在 Ascend910B2 上强制已有 OUTER hint 以直接覆盖 WorkspaceArg 路径：

- 生成 partial/combine 两个 Triton kernel；
- `rsplit_nsplit`、`rsplit_id`、`ws_ptr` 均出现；
- workspace 只分配/释放一次，顺序严格为 allocation→partial→combine→delete；
- 相对 CPU 与 NPU eager 均 allclose，dynamic replay 也 allclose；
- 最大绝对误差分别为 `6.103516e-05`、`7.629395e-05`，replay 为 `9.155273e-05`。

这证明 P-025 不只是 mock 契约通过，也能执行真实 workspace memory planning 与生成 wrapper。

## 6. 邻接 control-flow 缺口

为覆盖上游 per-subgraph planner，额外尝试了 large `torch.cond` 图。该图没有进入 wrapper：
experimental lowering 把 higher-order `cond` 当作普通 fallback 参数处理，在
`FallbackKernel.copy_input()` 读取 `Subgraph.dtype` 时失败。

因此本结果只说明 TE-LOW/control-flow 尚未支持该 higher-order op，不能用于否定 P-025；
P-025 对上游 subgraph planner 的保留由静态委托合同保证，真实 main-graph pointwise/rsplit
回归则验证其现有 NPU 路径。
