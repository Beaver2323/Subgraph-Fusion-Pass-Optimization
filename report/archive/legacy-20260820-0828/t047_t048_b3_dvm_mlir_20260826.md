# T-047/T-048：B3 DVM/MLIR pass 功能、修复与性能报告

## 结论

B3 的 8 条记录已完成源码、FakeTensor、source-built wheel 和真实 NPU 第一轮闭环：1 条
`supported-beneficial`、5 条 `supported-neutral`、1 条 `not-applicable`、1 条
`unsupported`。

| pass | 当前结论 | 核心证据 |
|---|---|---|
| `dvm_graph_fusion` | `supported-beneficial` | 15/15 NPU 回归；P50/P99 改善 24.20%/39.93%，首次编译 20.32→2.81 s，allocated peak 相同 |
| `annotate_mm_transpose_flags` | `supported-neutral` | transpose/contiguous 与 addmm bias 正负例通过；DVM matmul codegen 通过，未独立归因性能 |
| `decompose_k1_matmul_to_mul` | `not-applicable` | 直接 FX 正确，但真实 compile 在进入该 pass 前已由上游变成 `cast→mul→cast` |
| `insert_sum_fp32_prepost_cast_prims` | `supported-neutral` | P-012 修复 dtype 逃逸；人工禁用后 bare fp16 DVM sum native crash，属于可用性前置条件而非可安全配对的性能项 |
| `insert_promote_cast_by_pos_prims` | `supported-neutral` | mixed add/compare 正确插 cast，同 dtype 保持；DVM mixed/int64 用例通过 |
| `expand_to_reshape` | `unsupported` | 直接合同已修，但当前 partition capability 不接纳 expand/reshape/view，aggregate 中不可达 |
| `DvmMlirPostGradPass` | `supported-neutral` | previous pass 链与 UUID 正确；DVM backend 32/32，完整 MLIR 因缺 `torch_mlir` 阻塞 |
| `fold_sum_cast_to_dtype` | `supported-neutral` | 单用户正例 fold，多用户/显式 dtype/target mismatch 保持；未独立归因性能 |

这里没有手写 Triton：aggregate DVM 已有可用且更快的设备代码；sum 的问题是 dtype 能力门禁，
expand 的问题是 partition reachability，均不是缺少一个设备 kernel。

## 源码调用关系

`DvmGraphFusionPatch` 把 `torch._inductor.config.post_grad_custom_post_pass` 临时替换为
`dvm_graph_fusion()`。`GraphFusionPartitioner` 先按 `GRAPH_FUSION_SUPPORT_OP` 选连通分区，再在
每个 subgraph 内依次调用：

```text
decompose_k1_matmul_to_mul
  -> insert_promote_cast_by_pos_prims
  -> insert_sum_fp32_prepost_cast_prims
  -> expand_to_reshape
  -> dvm::fused_graph_* custom op
  -> DvmCodegenInterpreter
  -> @dvm.kernel
```

`annotate_mm_transpose_flags()` 不在上面四步里；它由
`torch_npu/_inductor/dvm/graph_build.py:DvmCodegenInterpreter.__init__()` 调用，为 mm/bmm/
addmm/baddbmm 写入 `trans_a`、`trans_b` 和可用 bias 标记。

另一条 DVM/MLIR scheduler 路径由 `npu_inductor_plugin.py` 安装
`DvmMlirPostGradPass`。它先调用已有 `post_grad_custom_post_pass`，再调用
`fold_sum_cast_to_dtype()`。当前 DVM backend 可在没有 `torch_mlir` 时使用自己的 codegen；
`mlir` backend loader 则显式 import `torch_mlir`，本环境不能完成该分支的编译验证。

## T-048 性能与不可隔离项

### aggregate paired 结果

`aggregate_basic` 使用 `(512,1024)` fp16 的 add→mul→sum→add 图。baseline 为 default
Inductor，candidate 为 `DvmGraphFusionPatch`；每侧 3 个 fresh worker，warmup 10、runs 100，
各一轮 10-step profiler。

| 指标 | default baseline | DVM candidate | 变化 |
|---|---:|---:|---:|
| P50 | 0.279905 ms | 0.212175 ms | 改善 24.20% |
| P99 | 0.374470 ms | 0.224960 ms | 改善 39.93% |
| mean | 0.367714 ms | 0.213482 ms | 改善 |
| 首次 compile+run | 20,319.58 ms | 2,807.76 ms | 改善 86.18% |
| additional allocated peak | 2,560 B | 2,560 B | 相同 |
| task/step | 1 | 3 | DVM 更多 |
| device duration/10 steps | 205.46 μs | 109.02 μs | DVM 更短 |

default 是一个 `triton_per_fused_add_mul_sum_0`；DVM 每步为两个
`DvmAddBroadcastMulCastReduce` 加一个 `DvmCastAdd`。DVM 虽然 task 更多，但设备总时长、host
P50/P99、首次编译和内存 gate 全部通过，因此 aggregate verdict 是
`supported-beneficial`，不能仅凭 kernel 数把它误判为回退。

### K=1 与 sum 为什么没有 paired 数字

K=1 冒烟的 pass-before 快照已经是三个 cast 包围一个 `aten.mul.Tensor`；跳过
`decompose_k1_matmul_to_mul` 后仍完全相同。这说明当前 PyTorch decomposition 已先完成目标，
该 torch_npu 子 pass 在真实 compile 路径没有增量，记 `not-applicable`。

sum 冒烟中，candidate 子图是 `cast(fp32)→sum→cast(fp16)`，数值合同通过；人工跳过该 pass
后生成 bare fp16 `k.sum`/`k.store(..., dvm.float16)`，进程在首次执行 native segfault。按失败
规则已读取 `fx_graph_transformed.py` 和 `output_code.py`。这个人工 baseline 不可用，因此不能把
candidate 与崩溃路径做延迟比较；结论是该 pass 对当前 DVM reduce 可用性必需。
