# T-025/T-026：pad_mm / pad_bmm / pad_addmm NPU 审计

## 结论

当前产品状态仍是 `unsupported`：上游 `pad_mm.py::check_device()` 只允许
CUDA/XPU，torch_npu experimental backend 还会关闭 `shape_padding`。测试侧只绕过
device gate 后，mm、bmm、addmm 的 static fp16 contiguous 正例都能正确执行
`pad -> GEMM -> slice`，aligned 负例也不会误触发；因此下游功能承接不是缺口。

但三个首批 shape 的性能都明显回退，最终 replacement verdict 为
`rejected-performance-regression`。本轮不修改产品 gate，不重建 wheel，也不手写
Triton 复制独立 padding。

## 为什么 `force_shape_pad=True` 仍不触发 NPU

调用顺序是：

```text
should_pad_mm / should_pad_bmm / should_pad_addmm
  -> should_pad()
  -> can_pad()
  -> check_device()
  -> force_shape_pad / 性能启发式
```

NPU 在 `check_device()` 就返回 false，所以还没有机会进入
`force_shape_pad`。T-025 的 forced worker 只在进程内把两个 NPU 输入视为设备能力
通过，没有修改其他 shape、dtype、stride 或启发式逻辑。

## 功能结果

| Family | Positive 输入 | Forced joint graph | 正确性 | Aligned negative |
|---|---|---|---|---|
| mm | `(255,257)@(257,259)` | 2 pad + padded mm + 2 slice | max/mean error 0 | 不 pad，只保留 mm |
| bmm | `(4,127,129)@(4,129,131)` | 2 pad + padded bmm + 2 slice | max/mean error 0 | 不 pad，只保留 bmm |
| addmm | bias `(259,)` + mm shape | 2 pad + `full/cat` + padded addmm + 2 slice | max/mean error 0 | 不 pad，只保留 addmm |

这证明“产品没有开启 pass”和“后端无法执行 pass 产物”是两件不同的事。本例是前者，
而且 gate 在当前代表 shape 上具有性能合理性。

## 配对性能

每个 family/variant/round 都是独立 fresh process/cache，固定 seed；顺序为
`B1-F1 / F2-B2 / B3-F3`。每轮 warmup 10、runs 100，每次调用后同步 NPU。

| Family | baseline p50 | forced p50 | p50 改善 | baseline p99 | forced p99 | p99 改善 |
|---|---:|---:|---:|---:|---:|---:|
| mm | 0.213605 ms | 0.368780 ms | -72.65% | 0.232840 ms | 0.407260 ms | -74.91% |
| bmm | 0.215645 ms | 0.356485 ms | -65.31% | 0.232380 ms | 0.394350 ms | -69.70% |
| addmm | 0.233980 ms | 0.516225 ms | -120.63% | 0.249340 ms | 0.535490 ms | -114.76% |

三者都未通过“p50 改善严格超过 10%，p99 回退不超过 5%”的预登记 gate。

## Task 与显存解释

| Family | baseline tasks/step | forced tasks/step | baseline peak | forced peak | 增量 |
|---|---:|---:|---:|---:|---:|
| mm | 1 | 5 | 132,608 B | 411,136 B | 278,528 B |
| bmm | 1 | 5 | 133,632 B | 428,032 B | 294,400 B |
| addmm | 1 | 7 | 132,608 B | 412,160 B | 279,552 B |

mm/bmm 的 forced 路径每步包含两次 PadV3，每次拆为 memset 和 pad，再执行一次
GEMM。addmm 还增加一个 bias-zero Triton task 和一个 cat。padded mm/addmm 的 kernel
仅有约 0.3–0.4 μs 小幅变化，bmm 甚至略慢，无法覆盖额外任务。显存增量与根据
padded inputs、padded output backing 和 bias temporary 计算的理论上界基本一致，
不是泄漏。

addmm forced 的首次编译中位数为 17,594.01 ms，baseline 为 2,612.72 ms；bias
补零引入的 fresh Triton launcher 编译进一步放大首轮开销。

## 决策与下一步

1. 保持上游 NPU device gate，不在 torch_npu 注册等价 duplicate pattern。
2. 不用 Triton 重写独立 padding；这只会更换实现，不消除读写、额外 buffer 和任务。
3. 本首批性能 gate 已失败，不继续扩展 dtype、dynamic、backward 或产品实现。
4. 若未来模型中的大 shape/特殊 layout 数据证明 padding 后 GEMM 有显著收益，应先
   评估把 masked load 融合进专用 GEMM（vendor/CATLASS/AscendC/NPU Triton
   template），再重新执行正确性、p50/p99、task 和显存 gate。
5. 主线转入 P1 的 66 条 pass 记录；T-023 的 no-shim launcher 复验仍是独立环境支线。
