## T-077 Gumbel-max 实测

该性能 workload 直接派生自社区
`test/inductor/test_pattern_matcher.py::TestPatternMatcherLogging.test_gumbel_max_trick`：完整复用
`sample` 计算图、`float32[1000000,10]`、`temperature=0.8`、十分类理论分布和 10% 相对容差。
社区没有提供 Gumbel 专用 benchmark，本地只增加 pass OFF/ON、fresh-process 隔离、计时、显存与
generated-code 采集，没有改变 workload。

测试固定 Ascend910B2 物理 NPU 1、CANN 9.0.1、冻结 PyTorch/torch_npu commit，并在每个 worker
导入前固定 `triton_experimental`。OFF/ON 各三个 fresh process，顺序为
`OFF1-ON1-ON2-OFF2-OFF3-ON3`；每轮 warmup 10、runs 100。输入保持上游原合同
`float32[1000000,10]`，六轮十分类分布均在 10% 相对容差内，目标 counter 分别严格为 OFF=0、ON=1。

| 指标（三轮中位数） | OFF | ON | 改善 |
| --- | ---: | ---: | ---: |
| host p50 | 6.026030 ms | 3.266415 ms | 45.79% |
| host p99 | 6.204922 ms | 3.366158 ms | 45.75% |
| NPU Event p50 | 5.916540 ms | 3.154280 ms | 46.69% |
| NPU Event p99 | 6.010443 ms | 3.215566 ms | 46.50% |
| 首次编译+执行 | 36912.383 ms | 30589.326 ms | 仅作 fresh-cache 诊断 |
| 编译+运行 peak allocated | 322005504 B | 280004096 B | -42001408 B |
| 编译+运行 peak reserved | 358612992 B | 295698432 B | -62914560 B |

OFF 三轮 host mean±stdev 为 `6.027969±0.061073`、`6.036579±0.066874`、
`6.108608±0.102012 ms`；ON 为 `3.277520±0.076782`、`3.252711±0.059367`、
`3.312251±0.090681 ms`。没有删除离群轮次。

生成 wrapper 静态复核显示，OFF 保留 softmax/isfinite/any、随机指数、概率除法与 argmax 链，
共 8 个主要 dispatch call；ON 改为随机指数、log/neg/add 与 argmax，共 6 个主要 dispatch call。
这里是 generated-wrapper call 数，不冒充 profiler 的设备 task 数。性能改善与删除 softmax 链一致。

因此 `AU-apply-gumbel-max-trick` 从仅有功能上的 `BEHAVIOR_UNCHANGED` 升级为
`PERF_IMPROVED`。机器可读结果见
`results/current/T-077/performance_summary.json`，原始 summary SHA256 为
`64092ce90ea753769eef301548c7daebbfc6adab1b5744882f041d3c92e4b24f`。

### 测例来源、Pass 意图与测量层级审计

1. **与社区性能测例设计方法的关系**：社区没有 Gumbel 专用性能测例。本地 benchmark 完整复用
   社区功能测例的图、输入规模、dtype、temperature、统计分布容差和 counter，再按社区 B2B 性能
   测例的核心思路补充同一 compiled callable 的 OFF/ON、预热、重复测量和 speedup。不同点是社区
   B2B 直接调用 `benchmarker.benchmark(..., warmup=100, rep=500)`，本地使用 fresh process 加手工
   synchronize/Event 计时，并报告三轮 p50/p99；因此是“社区合同派生并对齐设计原则”，不是声称
   直接复用了不存在的 Gumbel 社区 benchmark。
2. **与 Pass 意图的关系**：输入图正是 `softmax(logits) / exponential_(1) -> argmax`，ON 侧
   counter=1 且 generated wrapper 删除 softmax/div 链；统计分布仍满足原社区合同。因此测试既证明
   目标 rewrite 真正发生，也避免只测一个与 pattern 无关的近似 workload。
3. **端到端范围**：host 指标覆盖一次已编译 subgraph callable 的 Python 调用、kernel launch 与
   同步，可称为“Pass/subgraph 调用端到端”；NPU Event 是该 subgraph 的设备区间；首次编译+执行
   另作诊断。当前没有完整模型、训练 step 或应用级端到端 benchmark，不能把上述数据表述成
   full-model E2E 收益。

## T-077 B2B GEMM capability 与社区网格

社区已有 `plain`、`GELU`、`GELU-MLP` 三个 opt-in 性能测例：FP16、`M=[128,256,300,400,512]`、
`N=[16,20,32,40,50,64]`，每类 30 点，warmup 100、rep 500；逐点 speedup 和几何平均只打印，
收益断言已因 flaky 注释。探针没有另造 shape，而是复用这一网格，并只做两项测试态最小适配：

1. 让 NPU FakeTensor 仅在调用 upstream `is_b2b_gemm_good_on` 时复用 CUDA profitability policy；
2. 为 upstream `TritonTemplate` 的 benchmarker 补 NPU device-event dispatch，使 12 个 Triton choices
   能与 upstream 自带的 unoptimized fallback 正确 autotune。

六个社区功能变体中，4 个正例 matcher 命中、2 个负例保持不命中，正确性 6/6；但 4 个正例均由
autotune 选择 fallback。对完整 90 点静态复算后，upstream heuristic 只接受 26 点、拒绝 64 点。
实际执行 12 个社区代表/边界点，其中 8 点进入 autotune、4 点由 heuristic 拒绝、融合模板获选 0 点。
覆盖包括 plain 3/12、GELU 3/12 和 GELU-MLP 全部可命中点 2/2。

8 个进入 autotune 的点中，最佳 Triton 候选比 fallback 慢 30.23%～116.30%。因此这里不应继续做
“pass ON 后的 steady-state”伪对比，因为 ON 的最终 generated code 就是 fallback；正式 verdict 为
`CAPABILITY_REJECTED_NO_EFFECTIVE_TEMPLATE`，保留 NPU device guard。结构化证据见
`results/current/T-077/b2b_capability_assessment.json`。

## T-077 decompose 三单元实测

社区没有 decompose 专用性能测例。本地性能 workload 严格从各自社区功能正例派生，复用原始 shape、
dtype 和 `1e-3` correctness 容差，只新增 OFF/ON fresh process、host/NPU Event、峰值内存与 generated
code 采集。ON 仅在测试态让 NPU 复用 CUDA shape policy，未修改产品源码；MM 两臂均应用
`dfbcc25` 等价 small-mm correctness guard，确保只比较目标 decomposition。

| 单元 | 社区正例 | host p50 | Event p50 | Event p99 | 结论 |
| --- | --- | ---: | ---: | ---: | --- |
| decompose-BMM | `B=10240,M=K=N=2` | 回退 11.44% | 回退 15.07% | 回退 6.02% | `PERF_REGRESSED` |
| decompose-MM | `M=20480,K=5,N=2` fp32 | 回退 7.24% | 回退 11.38% | 回退 1.62% | `PERF_REGRESSED` |
| dynamic decompose-addmm | `M=19494144,K=N=8` | 回退 691.73% | 回退 758.05% | 回退 737.26% | `PERF_REGRESSED` |

BMM/MM 使用 OFF/ON 各三进程、warmup 10、runs 100；addmm 使用各三进程、warmup 5、runs 30。
addmm ON 的峰值 allocated 还增加 `3,119,066,624` bytes、reserved 增加 `2,967,470,080` bytes。
三单元都能命中并正确运行，说明失败不是 capability 缺失，而是 CUDA-oriented decomposition 在
Ascend910B2 上不盈利。故三项均保留 NPU device guard，不提交开放修复。机器可读结果位于
`results/current/T-077/decompose_*_performance_summary.json`。

上述全部是已编译 Pass/subgraph callable 的微基准，不是完整模型、训练 step 或应用级 E2E；只有未来
出现代表性模型时，才增加 full-model E2E 验证。
